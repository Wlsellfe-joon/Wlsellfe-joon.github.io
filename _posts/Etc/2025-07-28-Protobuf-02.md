## A Valid proto3 Example

```protobuf
syntax = "proto3";

package example.tasks;
option csharp_namespace = "Example.Tasks";

message DataInfo
{
  string key = 1;
  bytes value = 2;
}

message SubTask
{
  string code_name = 1;
  uint32 count = 2;
  repeated DataInfo data_info = 3;
}

message MainTask
{
  SubTask subtask = 1;
  string task_result = 2;
  optional string error_message = 3;
}
```

기존 예제의 `repeated data_info = 3`처럼 타입이 빠진 필드는 유효하지 않다. 모든 필드는 `[modifier] type name = number;` 구조를 가져야 한다.

## Cardinality and Presence

### Singular

modifier가 없는 scalar field는 기본값을 가진다. 문자열은 `""`, 숫자는 `0`, bool은 `false`다. 값이 기본값이면 “명시적으로 설정됨”과 “전송되지 않음”을 구분할 수 없다.

### optional

`optional string error_message = 3;`은 값의 존재 여부를 추적한다. C# generated code에서는 `HasErrorMessage`와 `ClearErrorMessage()` 같은 API가 생성된다.

### repeated

`repeated DataInfo data_info = 3;`은 0개 이상의 값을 순서대로 보관한다. C#에서는 `RepeatedField<DataInfo>`가 생성된다. repeated와 map은 비어 있음과 미전송을 구분하지 않는다.

### required

`required`는 proto2의 legacy 기능이며 proto3에서는 사용할 수 없다. 필수 값은 애플리케이션에서 검증하거나 presence가 필요하면 `optional`, message field, `oneof`를 조합한다.

## Scalar Types

Protobuf에는 `uint8`이나 `uint16`이 없다. 작은 범위에는 `uint32`를 사용하고 애플리케이션에서 범위를 검증한다.

- `bytes`: 임의의 바이트 배열. C#에서는 `ByteString`
- `string`: UTF-8 텍스트
- `uint32`, `uint64`: 부호 없는 정수
- `sint32`, `sint64`: 음수가 많은 값에 적합한 ZigZag 인코딩
- `fixed32`, `fixed64`: 고정 크기 인코딩이 유리할 때 사용

## Three Naming Rules

```protobuf
string task_result = 2 [json_name = "task_result"];
```

1. **Proto field name**: `task_result`
2. **Generated C# property**: `TaskResult`
3. **Default ProtoJSON key**: `taskResult`

`json_name`은 generated C# 프로퍼티 이름을 바꾸지 않는다. ProtoJSON 출력 key를 지정한다.

기본 출력:

```json
{ "taskResult": "ok" }
```

`json_name` 지정 후:

```json
{ "task_result": "ok" }
```

파서는 일반적으로 lowerCamelCase와 원래 proto 이름을 모두 허용한다. 전체 출력에 snake_case가 필요하면 formatter의 원래 필드 이름 보존 옵션도 검토한다.

## Field Number Rules

- 배포한 번호의 의미를 바꾸지 않는다.
- 1–15는 tag 인코딩이 작으므로 자주 등장하는 필드에 우선 배정한다.
- 삭제한 번호와 이름은 `reserved` 처리한다.
- 같은 message 안에서 번호를 중복하지 않는다.
- JSON 이름 변경은 binary wire format을 바꾸지 않지만 JSON consumer에는 breaking change일 수 있다.

## Compile and Inspect

```powershell
protoc --proto_path=. --csharp_out=Generated sample.proto
```

생성 결과의 `TaskResult`, `RepeatedField<DataInfo>`, `HasErrorMessage`를 비교하면 field 종류에 따른 API 차이를 이해하기 쉽다. generated file은 직접 수정하지 말고 `.proto`를 변경한 뒤 다시 생성한다.
